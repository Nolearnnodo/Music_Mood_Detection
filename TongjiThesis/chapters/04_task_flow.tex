\chapter{任务分析与交互流程设计}\label{chap:task-flow}

需求并不会自动告诉我们「用户该走哪几步」。本章把上一章相对静态的需求与 Persona 转换为动态的「\emph{用户做什么}」与「\emph{系统如何回应}」：从一张任务一览开始，依次借助使用行为分析、顺序分析以及故事讲述这三种粒度互补的工具去描绘核心任务，最后用页面跳转图与交互结构图把零散的任务拼成一张可在大脑中重建系统的全景。

\section{用户任务一览}

\cref{tab:task-list}~按「使用频率 $\times$ 关键程度」两个维度列出系统支持的全部用户任务。\textbf{使用频率}反映用户多久会触发一次，\textbf{关键程度}则反映任务是否承载本系统的核心价值——\emph{T1}（摄像头识别 + 一键推荐）、\emph{T2}（手动选择 + 推荐）与 \emph{T3}（聊天 + 推荐）是三条互为冗余的核心路径，对应三种 Persona 的偏好。其余任务围绕「曲库管理、自我观察、群体陪伴」三个外围价值展开，频率较低、关键度也较弱，但它们共同构成了系统的完整使用体验。

\section{使用行为分析}

使用行为分析（action analysis）把一个任务在用户视角下拆成「用户动作 — 系统响应 — 用户感受」的连续短单元，便于发现交互摩擦发生在哪一步。本节以 T1（摄像头识别 + 一键推荐）为例，把这条最关键的路径走一遍。

打开页面那一刻，用户面对的是一片以情绪输入面板为主、底部驻留浮动播放器的首页。对于第一次使用的用户，最大的不确定来自「我是不是要点摄像头」这一隐含问句。系统通过摄像头按钮上的小图标 + 一句小字说明（"点击开启摄像头识别"）承担了一半的提示责任，另一半则交给浏览器自身的权限弹窗。一旦用户授权，face-api.js 会在浏览器内对视频流做本地推理，每帧给出一个 7 类表情的概率分布。考虑到瞬时表情过于敏感（哪怕只是嘴角轻微的抽动也会让 sad 的置信度短暂高于 neutral），系统并不直接把瞬时识别结果送入推荐管线，而是用一个 1.2 秒的滑动窗口做\emph{稳定判定}：只有当某一类表情的平均置信度持续高于阈值、并且没有更高的次选时才会亮起「已稳定」徽标。这一短短的等待事实上承担了双重角色——它既过滤了噪声，也给了用户一个「让我先确认一下」的窗口，避免被识别结果突袭。

接下来，用户要做的只有两个动作：在「匹配 / 安抚」按钮中选一个，然后按下「一键推荐」。系统在按钮上立即显示一个小型加载动画，然后向后端发起一次 \texttt{GET /api/playlist/generate} 请求；后端在 SQL 层完成基于情绪距离、用户反馈、新鲜度与最近播放时间的复合打分（见\cref{sec:reco}），返回一个携带评分明细的歌单。前端在收到响应之后并不只是把列表渲染出来，更重要的是触发\textbf{主题切换}与\textbf{背景过渡}——\texttt{<html data-mood="xxx">} 的属性一变，整个页面的色调、Aurora 流动背景的色彩 stop、玻璃卡片下透出的色温都会跟着柔和过渡。这一刻是整个 T1 任务中对用户感受最关键的瞬间：它把抽象的「系统理解了你」翻译成了\emph{可被肉眼感知}的回应。最后，第一首歌自动开始播放，黑胶旋转动画启动，用户在右下角的余光中确认「它真的在放」，整条 T1 路径就此完成。

T2 与 T3 是 T1 的两条变体。T2 跳过了摄像头授权与滑窗稳定，因此从「打开」到「出歌」之间通常只有 4 步、平均完成时间 25 秒上下；这也是 Aria 这一类拒绝摄像头的用户优先选择它的原因。T3 在输入端引入了自然语言聊天，于是多了一次往 LLM 的网络调用——这也意味着它在最理想的情境下并不比 T1/T2 更快，但在用户「自己也说不清楚情绪」的时候反而是最自然的入口。

\section{顺序分析}

把 T1 在时间轴上展开就得到了\cref{fig:seq-t1}~所示的顺序图。它的价值并不在于把每一次消息都画清楚，而在于让设计者一眼看出\emph{哪些环节发生在客户端、哪些发生在后端、哪些跨越了多次往返}。可以读出两条对设计判断有用的观察：其一，摄像头识别与滑窗稳定都发生在浏览器内，因此整条 T1 路径不依赖网络；其二，从用户按下「一键推荐」到拿到歌单整个流程只有一次后端调用，对带宽和延迟的要求都很低。这两点正是「本地优先」原则在性能维度上的回响。

\section{故事讲述：从 Persona 视角走一遍}

故事讲述（storytelling）的好处在于强迫设计者放下「系统应当如何」的视角，回到「某个真实的人在某个真实的时刻会如何使用」的视角。下面三段叙述分别对应三位 Persona——它们既不是评估实录，也不是营销文案，而是设计推进时课题组反复回到的「参照故事」。

\textbf{凌晨一点的小南。}~小南刚关掉编辑器，机械地把椅子往后靠了靠。他没打算搜索什么，于是直接打开了 Mood Radio 的电台页。摄像头小窗在角落安静地工作，几秒之后屏幕上方亮起了「sad，置信 0.78」的徽标——这并不是诊断，只是一个识别结果，他甚至无需点击确认。小南选了「安抚」，按下「一键推荐」，屏幕背景就从冷蓝缓缓过渡到靛紫；第一首低唤醒的钢琴曲已经在右下角的浮动播放器里转起了黑胶。整条流程没有打字，没有滚动，也没有「让我先看看歌单再决定播哪首」的犹豫。从设计者的角度看，这段故事印证了一件事：在情绪低落的瞬间，最受用的不是更多的选择，而是\emph{被减去}的选择。

\textbf{咖啡馆里的 Aria。}~周二上午，Aria 把笔电摆在咖啡馆窗边，准备完成一份提案。摄像头是不会开的——身边随时有人路过。她在 \texttt{/radio} 页面跳过摄像头按钮，直接点了「focused」这枚手动情绪按钮，再按下「匹配」与「一键推荐」。系统返回了 8 首高 V 低 A 的器乐曲，并在页面右上角小字标注着「私有，仅本地」。这句小字看似只是一个提示，却是 Aria 决定把 Mood Radio 留在 Dock 里的理由——她需要的是一个明确告诉自己「我不会偷偷上传你的数据」的产品。

\textbf{晚饭后的阿陈。}~阿陈把窗帘拉上，让笔电进入全屏。他没有从主页开始，而是直接打开 \texttt{/mood} 的 Russell 二维图，鼠标在右下角「高 V 低 A」的歌曲群里圈了一下，按下 \texttt{Enter}。整页背景立刻被一张专辑封面的暖橙色蒙版接管，黑胶开始转动，铃声、贝斯、底鼓在 7 秒一圈的旋转节奏里铺展开。这一刻视觉、听觉与他口袋里那张实体黑胶之间产生了某种不易言说的对应——这不是「准确推荐了一首歌」，而是「构成了一个氛围」。

三个 Persona 的故事看起来风格迥异，但它们其实在反复强化同一件事：本系统应当面向多种使用偏好做出有诚意的回应，而非把所有人都引向同一条「正确」的路径。

\section{交互结构图}

交互结构图（interaction structure diagram）把系统按「功能维度」而非「页面维度」组织起来，揭示用户在大脑中应该如何理解 Mood Radio。\cref{fig:interaction-structure}~把功能归为四组：情绪输入、推荐与播放、个人化与反馈、群体与隐私。前两组之间存在显式的「输入 $\to$ 输出」关系；第三组「个人化与反馈」是这条路径上的反向闭环——用户每一次的喜欢或不喜欢都会回流到 SQL 端的打分；而第四组「群体与隐私」更像是一条横向的「外壳」，把所有功能在 Aria 这一类隐私敏感用户面前划出一道明确的边界。
