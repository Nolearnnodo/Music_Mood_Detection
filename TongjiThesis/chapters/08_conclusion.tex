\chapter{总结与展望}\label{chap:conclusion}

\section{工作总结}

本课程设计以「人机交互导论」课程要求为出发点，围绕「让音乐推荐理解用户的此刻情绪」这一目标，设计并实现了名为 Mood Radio 的本地音乐电台 Web 应用。整体工作覆盖了从需求调研、系统架构、关键算法到交互细节的完整链路，可归纳为如下三个层面：

\begin{itemize}
  \item \textbf{设计层面}。基于 42 人的小规模用户调研，本项目抽取出「低负担输入、用户可控、可解释、本地优先、沉浸感与一致性」五条贯穿全局的设计原则，并据此进行功能取舍。
  \item \textbf{工程层面}。系统在三周左右的时间内完成了 React 前端的 8 个页面、25 个以上 REST 接口的 C++ 后端、SQLite 持久层与 Python 离线分析脚本的协同实现，并解决了 ncnn 推理失真等关键工程问题。
  \item \textbf{交互层面}。系统提供了摄像头表情、手动选择、自然语言聊天、时段电台、头部手势 5 种情绪输入通道，配合 7 套情绪主题、Aurora 背景与黑胶旋转封面，构建了一个完整的、可被用户感知的情绪反馈环。课堂模拟评估显示，9/10 用户认可本地隐私设计，8/10 用户能够理解推荐逻辑。
\end{itemize}

总体而言，本项目较为完整地实践了 HCI 中「多模态输入、情境感知、用户控制、可解释性、隐私保护」等核心原则，体现了人机交互从「工具响应操作」向「系统理解情境」转变的研究思路。

\section{局限性}

诚实地看，本课程设计仍存在不少局限：

\begin{enumerate}
  \item \textbf{ncnn 推理仍不可用}。C++ 端模型推理输出范围错误，目前依赖 Python 离线脚本绕过。最终方案需要重做 ONNX$\to$ncnn 转换，并把 FeatureExtractor 与训练流水线严格对齐。
  \item \textbf{在场感非真实时}。系统通过 60\,s 心跳 + 10\,s 拉取实现群体在场，端到端延迟约 1 分钟；真正的多人协同需要 WebSocket 支持。
  \item \textbf{推荐画像简单}。复合打分目前只对「喜欢」加固定 1.5 分，并未基于用户长期反馈动态调整目标 V/A 中心，画像粒度较粗。
  \item \textbf{评估规模有限}。$N = 10$ 的课堂模拟评估只能提供方向性结论，无法给出严格的统计显著性结果。
  \item \textbf{弱光识别与小曲库问题}。face-api.js 在弱光、遮挡场景下识别不稳定；当个人曲库较小时，复合打分容易反复推送少数高分曲目。
\end{enumerate}

\section{后续可扩展工作}

围绕上述局限，本课程设计在后续可以沿如下方向扩展：

\begin{itemize}
  \item \textbf{修复 ncnn 推理}：让 C++ 路径真正可用，摆脱对 Python 子进程的依赖；
  \item \textbf{偏好画像 v3}：把所有「喜欢」歌曲的 V/A 均值作为「我喜欢的中心」，作为额外打分项，并随用户反馈动态更新；
  \item \textbf{WebSocket 在场推送}：实现真正的群体实时同步，支持「正在听同一首歌」的高刷新展示；
  \item \textbf{多设备同步}：通过 UUID 关联，跨浏览器同步播放历史与喜好；
  \item \textbf{节拍/BPM 同步}：让黑胶旋转速度与歌曲 BPM 同步，进一步增强沉浸感；
  \item \textbf{情绪推荐解释生成}：在每条推荐结果旁，由 LLM 实时生成一段「为什么推这首」的解释短文；
  \item \textbf{更系统的用户评估}：将课堂模拟评估扩展为正式的 within-subject 实验，对推荐准确率、操作时间、主观满意度等指标进行更细致的对比。
\end{itemize}

总的来说，Mood Radio 在课程设计的尺度内做了一次比较完整的「从识别到回应」的 HCI 探索。好的情绪交互系统不应只停留在「识别情绪」，更重要的是\emph{识别之后如何回应、如何解释，并始终尊重用户的控制权与隐私边界}——这是本项目希望传达的核心立场。
