\chapter{关键功能与算法实现}\label{chap:implementation}

设计意图与运行系统之间往往隔着一段不平整的工程地形。本章从 Mood Radio 中挑出四块最具代表性的实现：V/A 情绪坐标的建模与一次中途修复、多通道情绪输入的统一融合、复合打分推荐算法的演进，以及聊天功能背后的 LLM 子进程代理。它们既反映了课题组对核心算法的选择，也包含了若干「实测之后才意识到必须妥协」的工程判断。

\section{V/A 情绪坐标的建模与修复}\label{sec:onnx-fix}

\subsection{二维情绪坐标}

系统沿用 Russell 在 1980 年提出的二维情绪模型\cite{russell1980circumplex}，把每一首歌的情绪都看作平面上的一个点 $(v, a)$，其中 $v$（Valence）反映「愉悦--不愉悦」的水平轴，$a$（Arousal）反映「平静--激活」的垂直轴。课题组沿用训练集 DEAM 的取值范围，让 $v, a \in [1, 9]$，使得「中性」对应于 $(5, 5)$。对人脸表情，则通过一张静态映射表（\cref{tab:emotion-mapping}）把 face-api.js 输出的 happy / sad / angry 等类别翻译为同一空间中的坐标，从而让「人的情绪」与「音乐的情绪」可以在同一张二维图上做距离运算。

\subsection{距离与回退}

把人与音乐都放到同一坐标空间之后，推荐的第一步就回到了非常朴素的几何问题——给定目标点 $(v^\star, a^\star)$，找出曲库中距离最近的若干首歌。系统使用平面欧氏距离作为基本度量：
\begin{equation}\label{eq:dist}
  d\bigl((v_i, a_i), (v^\star, a^\star)\bigr) = \sqrt{(v_i - v^\star)^2 + (a_i - a^\star)^2}.
\end{equation}
然而，简单的「最近 $K$ 首」在实际使用中很快就遇到了麻烦。用户在界面上能够指定一个搜索半径 $r$（默认值 1.2），这一参数在曲库较大时表现良好，但在 50 首左右的小曲库上经常出现「半径之内一首都没有」的情况。课题组没有让系统抛错，而是让它自动放宽——按照 $r \rightarrow 1.5r \rightarrow 2.5r \rightarrow 4r$ 的级数渐次扩张，直到取到至少一首候选为止。这一机制本质上是 HCI 中「容错与优雅降级」原则的具体落地：把「无歌可推」的尴尬替换为「半径稍大也能听上」的可接受结果。

\subsection{ncnn 推理失真与离线修复}

V/A 数值是整条推荐链路的基础，因此当它出错时，所有下游都会跟着错。本项目最早采用 \texttt{ncnn} 在 C++ 端执行 ONNX 模型推理，初衷是部署轻量、跨平台兼容性好。然而实测中，同一首歌在 \texttt{ncnn} 路径上输出的 V/A 值落在了 $[-135, +138]$ 这样一个完全离谱的范围里——而正常的输出应当被 sigmoid 压在 $[1, 9]$ 之间。这意味着曲库被全部标错了。

为了定位问题，课题组对比了三条推理路径：原始 C++ 路径走 \texttt{ncnn}，第二条 C++ 路径换成 \texttt{onnxruntime}，第三条则是 Python 端的 \texttt{onnxruntime + librosa} 离线脚本。后两者得到的结果与训练时的标定值高度一致，这一对比从侧面证明问题既不出在预处理公式（虽然 C++ 端的 \texttt{log10(10000 x + 1)} 看上去和训练时 \texttt{librosa.power\_to\_db} 不太一样，但同一公式在 onnxruntime 路径下也能跑出正确结果），也不出在 ONNX 模型本身——大概率是 \texttt{ncnn} 在模型转换或推理实现中出现了与本模型不兼容的某种细节。

考虑到课程时间，本项目最终采取了「绕过 ncnn」的实用策略：写了一个 \texttt{scripts/analyze\_all.py}，在 Python 离线路径上以与训练完全一致的 \texttt{librosa} 流程对全库重算 V/A，再把结果写回 SQLite。修复后 77 首歌的分布如\cref{tab:va-distribution}~所示：取值落在合理区间内、分散度也接近训练集；按 V/A 排序的结果与人工主观判断高度一致——伤心金曲集中在 V 低端、J-pop 高能曲目集中在 A 高端、纯古典的 A 值偏低。这一修复让系统重新获得了可用的曲库标注，也为后续课堂演示扫除了最大的障碍。

\section{多通道情绪输入}

\subsection{统一入口}

五种情绪输入通道（摄像头、手动、聊天、时段、头部手势）在前端从五个完全不同的组件中诞生，但最终都会收敛到同一个回调 \texttt{\small handleEmotionGenerate(stableEmotion,\linebreak[1] moodTarget, strategy)}。这一选择源于「单一真理源」（Single Source of Truth）的状态管理理念——下游所有依赖情绪状态的逻辑（推荐请求、心情日志写入、主题切换、心跳上报）都只需要订阅这一个事件，而不必逐一去关注是谁触发了情绪。\cref{tab:channel}~给出了五种通道的实现方式与输出格式。

「策略」字段统一为 \emph{match}（顺应当前心情）与 \emph{comfort}（安抚/反向调节）两种。后者在数学上等价于把目标坐标向中性参考点 $(5, 5)$ 拉近一定比例——例如愤怒情绪 $(3.5, 7.5)$ 在「安抚」策略下被拉到 $(4.5, 6.0)$ 附近，使推荐结果更接近平静而非进一步激化。

\subsection{头部手势的稳健识别}

在五条通道中，头部手势是最容易出问题的一条。课题组在实测中观察到两类典型的「误触发」：第一类是用户把头甩到位之后再回正，回正过程中会再次跨过方向阈值，于是产生一个反向的 \texttt{swipe}；第二类是用户静坐时小幅度的自然晃动，偶尔会被识别成 \texttt{shake}。两类问题如果不解决，整个手势通道就会变得「带着用户走」而非「跟随用户」。

为此，课题组并没有引入复杂的姿态模型，而是写了一个相当朴素但有效的状态机（\cref{algo:gesture}）。它的核心思路是用「滑窗内偏离起点的最大幅度」\texttt{peakDx} 来判定方向，而不是「滑窗末尾的位移」\texttt{xNet}——前者意味着用户只要在过程中达到过足够大的偏移就算成功，而不必把头一直保持在偏移位置；后者则会被回正动作清零。引入一段 1 秒的「屏蔽期」可以吞掉触发后的所有回正帧，避免反向 swipe。最后，叠加「总位移 + 反转次数 + 峰值幅度」三重门槛之后，静坐时的微小晃动也被过滤掉。值得一提的是，由于前端摄像头预览启用了 \texttt{scaleX(-1)} 的水平翻转，方向语义需要再翻一次，否则会出现「向左挥头反而切下一首」的误解，这一细节通过一个 \texttt{mirrored} 参数集中处理。

\begin{algorithm}[!htb]
  \caption{头部手势识别状态机（简化版）}\label{algo:gesture}
  \begin{algorithmic}[1]
    \Require 鼻尖关键点 $(x_t, y_t)$，滑窗长度 $W$，方向阈值 $\theta_d$，
      反转次数阈值 $\theta_r$，静坐总位移阈值 $\theta_s$，屏蔽时长 $T_b$
    \Ensure 离散手势 $g \in \{\text{swipe\_left}, \text{swipe\_right}, \text{shake}, \text{nod}, \emptyset\}$
    \State 维护近 $W$ 帧的坐标缓冲 $B$ 与上次触发时间 $t_{last}$
    \If{$t - t_{last} < T_b$} \State 清空 $B$；\Return $\emptyset$ \EndIf
    \State 计算 $\text{peakDx} = \max_t |x_t - x_0|$，$\text{totalPath} = \sum_t |x_t - x_{t-1}|$，反转次数 $r$
    \If{$\text{totalPath} < \theta_s$} \State \Return $\emptyset$ \Comment{静坐噪声直接放弃} \EndIf
    \If{$r \geq \theta_r$} \State $t_{last} \gets t$; \Return $\text{shake}$ \EndIf
    \If{$\text{peakDx} \geq \theta_d$}
      \State $g \gets$ \textbf{if} $\text{peak}>0$ \textbf{then} \text{swipe\_right} \textbf{else} \text{swipe\_left}
      \State $t_{last} \gets t$; \Return $g$
    \EndIf
    \State \Return $\emptyset$
  \end{algorithmic}
\end{algorithm}

\section{复合打分推荐算法}\label{sec:reco}

\subsection{v1：朴素的距离过滤}

推荐的最初版本（\texttt{playlist\_v1}）相当朴素：在情绪距离的平方半径之内取所有候选，按距离升序排出前 $N$ 首：
\begin{equation}
  \mathcal{R}_1 = \bigl\{ s_i \mid (v_i - v^\star)^2 + (a_i - a^\star)^2 \leq r^2 \bigr\}.
\end{equation}
这一形式直观、好实现，但只考虑了「歌曲与当前情绪有多近」这一个维度，导致两类不愉快的体验：用户标记过「不喜欢」的曲目依然会被推送，因为算法根本不看反馈；同一首歌在同一情绪下被反复推送，因为算法不知道「这首歌十分钟前刚被播过」。换句话说，v1 把推荐当作纯几何问题，遗漏了用户与时间这两个维度。

\subsection{v2：复合打分}

v2 把上述问题整体重构。课题组把「情绪距离」「喜欢/不喜欢」「新鲜度」「最近播放」四个信号融合进同一个打分公式（\cref{eq:score}），并把整段计算下推到 SQL 层一次性完成——避免在 C++ 端做大量内存级排序：

\begin{equation}\label{eq:score}
  \mathrm{score}(s_i) = -d_i^2 + \mathbb{1}[\text{like}] \cdot 1.5 + \mathbb{1}[\text{never}] \cdot 0.4 - \mathrm{recencyPenalty}(s_i),
\end{equation}
其中 $d_i$ 沿用\cref{eq:dist} 的距离定义；\texttt{like} 加 1.5 分体现「用户喜欢」对当前推荐的正向偏置；\texttt{never} 加 0.4 分用于鼓励那些从未播放过的曲目，避免用户的库被自己长期的偏好「困死」在同一片小区域内；最后一项 $\mathrm{recencyPenalty}(s_i)$ 是关于「最近一次播放距今时长」的分段惩罚函数：
\begin{equation}\label{eq:recency}
  \mathrm{recencyPenalty}(s_i) = \begin{cases}
    3.0, & \Delta t \leq 30\ \text{min} \\
    1.4, & 30\ \text{min} < \Delta t \leq 2\ \text{h} \\
    0.7, & 2\ \text{h}  < \Delta t \leq 6\ \text{h} \\
    0.2, & 6\ \text{h}  < \Delta t \leq 24\ \text{h} \\
    0,   & \text{otherwise}.
  \end{cases}
\end{equation}
惩罚的递减是经过几次小规模实验才定下来的：太陡（例如「30 分钟内 -10 分」）会让用户在两次刷新之间几乎换掉整个歌单，太缓又起不到「别再推这首」的作用。被显式标记为「不喜欢」的曲目以及用户在 UI 中指定的「最近 $N$ 分钟内播过」的曲目直接在 SQL 层用 WHERE 过滤掉，不参与打分；若打分后候选过少，再走\cref{sec:onnx-fix}~末尾所述的半径回退。

\subsection{可解释性反馈}

复合打分本身在用户面前是一行数字。如果用户不知道这首歌为什么被排在第二位，那么「可解释」就是一句空话。为此，系统在 \texttt{/api/playlist/generate} 接口上增加了一个 \texttt{debug\_score=true} 的查询参数；开启后每一条返回项都会携带 \verb|{score, dist, feedback, last_played_min_ago}| 四个字段。前端则把这些字段翻译为三类小徽标——「\textbf{喜欢}」表示这首曲目在用户的 \texttt{user\_feedback} 表中标记过 like，「\textbf{新鲜}」表示从未在 \texttt{play\_history} 中出现过，「\textbf{最近}」表示近 24 小时内播过。这三枚小徽标看起来不起眼，却把后端的复合打分通过最小可读单元呈现给了用户，让推荐过程不再是黑箱。

\section{LLM 子进程代理与隐私设计}

\subsection{动机：前端配置 + 后端代理}

\texttt{/chat} 页允许用户用自然语言描述当下情绪（比如「今天有点焦虑，想听点能让我平静下来的歌」），由 LLM 返回 \texttt{\{reply, mood, target\}} 这样的结构化 JSON。这一功能要落地，首先要决定一个看似简单实则关键的问题：API Key 放在哪里？

如果让前端直接调用 LLM，那么 Key 就必须以某种形式嵌入前端代码，任何打开 DevTools 的用户都能拿到——这显然不可接受。如果把 Key 长期保存在后端，又违背了\cref{chap:requirement}~中提出的「本地优先」原则：用户安装 Mood Radio 时没有理由相信自己的 Key 应该被系统持久化。课题组最终选择了一种折中——「\textbf{前端配置、后端代理}」的方案：用户在 \texttt{/settings} 中填入 \texttt{base\_url} / \texttt{api\_key} / \texttt{model}，这份配置仅存放在浏览器 \texttt{localStorage} 中；用户在 \texttt{/chat} 发起请求时，前端把这份配置作为请求体的一部分 POST 给后端；后端将配置写入一个临时 JSON 文件、拉起 Python 子进程完成 LLM 调用，再读出结果回传给前端。整个过程结束时临时文件会被删除，Key 既不进入 SQLite，也不会出现在后端日志里。

\subsection{流程实现}

\cref{lst:llm}~是聊天链路在 Python 端的核心实现，省略了与本节无关的错误处理。可以看到，LLM 请求并未使用第三方 SDK，而是用 \texttt{urllib} 直接拼出 OpenAI 兼容的 chat completions 接口；返回的 JSON 经过 \texttt{clamp\_target} 收紧到合法范围后写入输出文件。这种「自包含、零依赖」的写法让 Python 端不必维护额外的虚拟环境，安装成本最低。

\begin{lstlisting}[
  language=Python,
  caption={LLM 子进程代理的关键实现（节选）},
  label=lst:llm,
  basicstyle=\ttfamily\footnotesize,
  escapeinside={},
  mathescape=false,
  float=!htb,
]
def chat(in_path: str, out_path: str):
    cfg = json.load(open(in_path, encoding="utf-8"))
    body = {
        "model":    cfg["model"],
        "messages": SYSTEM_PROMPT + cfg["messages"],
        "response_format": {"type": "json_object"},
    }
    req = urllib.request.Request(
        cfg["base_url"] + "/chat/completions",
        data=json.dumps(body).encode("utf-8"),
        headers={"Authorization": f"Bearer {cfg['api_key']}"},
    )
    with urllib.request.urlopen(req, timeout=30) as resp:
        data = json.loads(resp.read())
    parsed = json.loads(data["choices"][0]["message"]["content"])
    parsed["target"] = clamp_target(parsed.get("target"))
    json.dump(parsed, open(out_path, "w", encoding="utf-8"))
\end{lstlisting}

\subsection{隐私收益}

这一方案带来的隐私收益虽朴素却扎实。最关键的是 API Key 只在浏览器内长期存在，并在 LLM 调用结束之后从后端的内存与文件系统中彻底消失；其次是历史聊天与音乐文件均没有理由离开本机，因为 LLM 看到的「上下文」仅限于用户当前发送的几句话，不包含本地曲库或播放历史；最后，后端只在子进程持续的几秒之内短暂持有 Key，调用结束即被回收。需要承认的是，这一方案并不能彻底消除信任前提——用户仍然需要相信他们自己挑选的 LLM 服务方不会滥用聊天内容——但相对于「全端云推理」的常见做法，它已经把可被审计的隐私边界明确划了出来，与\cref{chap:requirement}~所归纳的「本地优先」原则保持一致。
